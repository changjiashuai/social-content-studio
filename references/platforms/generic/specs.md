# 通用平台规格总表（generic）

**这是本 skill 里唯一没有平台规则可引用的规格表。** 影片发在自有渠道，不存在「平台允许什么」的问题，因此本表只规定**兜底范围**与**共用媒体标准**；真正的约束来自 `SKILL.md` 的「通用平台 · 产品片」章节与 `motion-film/` 下的 13 个分册。

机器可读版本：`scripts/social_specs.json` → `platforms.generic`。

---

## 1. 影片（`generic/motion-film`）兜底参数与片型

| 项 | 兜底范围 | 说明 |
|---|---|---|
| 画幅（宽/高比） | 0.3 – 3.4 | 基本等于「自由」。竖版 9:16、横版 16:9、方形 1:1 都允许 |
| 时长 | 1 秒 – 60 分钟 | 兜底区间，仅用于挡住「0 秒文件」这类明显错误 |
| 分辨率短边 | ≥ 720 | 兜底下限；正式片按 1080p 起做 |
| 宽高必须为偶数 | 强制 | `yuv420p` 的要求，`check_delivery.py` 会拦 |
| 编码 | H.264（首选）/ H.265 | H.265 兼容性差，默认导 H.264（同视频号口径） |
| 音轨 | 不强制 | 用户要求静音时必须记录 `audioExceptionReason` |
| 封面比例 | 3:4 / 4:3 / 16:9 三种 | 三种都做，一次渲染出齐（见分册 `cover.md`） |

> 上表的数字**不是平台要求**，是本 skill 的兜底阈值。影片的真正验收标准是人工审片：主张是否可追溯、手法是否从内容推导、声音是否听过、首帧是否完整。

### 1.1 片型（`plan.json` 的 `filmKind`）

片型由**内容**决定，不预设。`check_delivery.py` 按片型分派必备项：

| 片型 | 什么时候用 | 必备项 | 原组件 |
|---|---|---|---|
| `product` | 讲产品的功能、价值或更新 | 至少一项可追溯的功能主张（`claim: true` + `source[]`） | 功能镜头必须有 `component`（A 级缺则报错） |
| `evidence` | 以数据或事实为主 | `evidence/FACTS.md` 或 `RESEARCH.md` | 不要求 |
| `explainer` | 讲清概念、机理、原理 | 同上 | 不要求 |
| `story` | 情感、人物、叙事为主 | 不要求主张；建议写 `fictionNote` 说明虚构部分 | 不要求 |

**不声明 `filmKind` 等于 `product`**，所以默认路径的严格度与 v1.3.0 及之前完全一致；放宽是主动声明，不是默认。
无论哪种片型，**都不许假造界面**：没有原组件时不画「像但不准」的 UI。

## 2. 共用媒体标准（`shared` 节点，全平台适用）

| 项 | 值 | 来源 |
|---|---|---|
| 像素格式 | `yuv420p` | 跨播放器兼容底线 |
| 音频编码 / 码率 | AAC / 192k | — |
| 采样率 | 44100 Hz | `loudnorm` 默认会提到 192kHz，必须显式指定 |
| 响度目标 | I = -15 LUFS / TP = -1.5 dBTP | 两遍 `loudnorm`（先测后应用） |
| 图片色彩空间 | sRGB | — |
| 单图体积上限 | 10 MB | 取各平台中最严的一档 |
| 字体栈 | 系统字体栈 | 见 `social_specs.json` → `shared.image.fontStack` |

媒体标准在 `scripts/social_specs.json` 里放在顶层 `shared`，**不属于任何平台**——它是所有平台线共用的底座。产品片的工程侧对应做法见 `motion-film/starter.md` 与 `motion-film/pipeline-notes.md`。

## 3. 两层自检的覆盖范围（诚实说明）

本形式有**两个**检查器，覆盖范围差异很大：

**① `scripts/video-line/check_delivery.py`（强，视频线自带）**

| 检查 | 会不会做 |
|---|---|
| `plan.json` 必填字段、宽高偶数、`style` 取值 | ✅ |
| 镜头 id 唯一、时间线无缝无叠、总长等于 `declared duration` | ✅ |
| 每个镜头有 headline、显式声明 `claim` | ✅ |
| `claim: true` 的镜头必须有 `source[]`，且 `file:`/`repo:` 源文件真实存在 | ✅ |
| 存在 `DIRECTION.md`，且有镜头表、有「因为 X」的推导句 | ✅ |
| 中英双语标题、中文无衬线、中英字体不同 | ✅ |
| 正式片至少一项有证据的功能主张 | ✅ |
| 动作 id 唯一、落在镜头内、`soundRequired` 与 cue 一一对应 | ✅ |
| cue 的听觉落点与动作对齐（容差 2 帧）、gain 范围、让位证据 | ✅ |
| 混音产物哈希与 `plan.json` 哈希一致（防陈旧报告） | ✅（给了 `--mix-report` 时） |
| 成片分辨率 / 帧率 / 时长与 plan 一致、音轨存在 | ✅（给了 `--video` 时） |
| 节奏指标（近静止帧占比、最长静止段、硬切次数） | ✅ 提示性质 |
| 前 5 帧墨量（首帧是否空白） | ✅ |
| 主张的**语义**是否成立 | ❌ 需人工核实 |
| 画面品味、裁切、安全边距、字幕实际可读性 | ❌ 靠审片（做法见 `pipeline-notes.md` 第 18/20/27 条） |
| 响度、音效可听度、音画同步的**听感** | ❌ 必须试听 |

**② `scripts/check_social_delivery.py`（弱，平台线兜底 + 内容溯源）**

平台侧仍只做：交付文件存在、视频可被 `ffprobe` 探测（有 ffprobe 时）、时长 > 0。**画幅、分辨率、封面比例、节奏、声音一律不校验**——产品片允许自由画幅，平台线那套比例判据在这里不适用。

但从 v1.2.0 起，它额外做一件与规格无关的事：读内容目录的 `evidence/FACTS.md`，核对上屏数字有没有登记出处（见 [内部溯源](motion-film/provenance.md)）。**它只保证「有登记」，不保证「登记的是真的」**——后者仍是人工核实。

| 溯源检查 | 会不会做 |
|---|---|
| `evidence/FACTS.md` 结构完整（主张 / 上屏内容 / 来源三列） | ✅ |
| 上屏数字能否在底账找到对应行 | ✅ 找不到只报 WARN（内部项，不阻断） |
| 标为「示意」却使用「官方数据显示」一类措辞 | ✅ 报 ERROR |
| 数字本身是否属实、引用是否被误读 | ❌ 人工核实 |

**溯源结论是内部核查项**，默认不出现在给用户的交付说明里；用户问起或证据链断裂时才用一句话说明。

**不得把任一检查器的「通过」当作影片已验收。** 交付说明里必须写清哪些环节是人工看过的、听过的。

## 4. 来源说明

本表不引用任何平台规则——没有平台。其中：

- 「共用媒体标准」来自编码与分发侧的通行做法（H.264 + yuv420p + AAC + `faststart`）与响度归一化的实测结论（见 `motion-film/pipeline-notes.md` 第 21–22 条）。
- 「兜底范围」是本 skill 自定的阈值，不声称来自任何第三方。

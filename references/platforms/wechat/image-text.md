# 微信图文（图片消息 / 小绿书）

**载体**：公众号「图片消息」。用户在微信里横滑浏览，展示比例 **3:4**；系统自动生成封面图。
**交付物**：一组 3:4 图片（推荐 1080×1440）+ 逐图配套文案 + 标题 + 首图封面方案 + 自检报告。

规格参数一律以 [微信官方规格总表](specs.md) 第二节为准；本文件讲**怎么做**。

---

## 1. 与视频线的关系

图文不是"视频的截图版"。它**复用**视频线的产品取材（第 3 步）与 `DIRECTION.md` 的主视觉规范，但叙事逻辑换一套：

| | 视频线 | 图文线 |
|---|---|---|
| 时间维度 | 靠时间轴推进，观众被动跟随 | 靠**横滑顺序**推进，观众主动决定看第几张 |
| 信息密度 | 每 2–3 秒一个视觉变化 | 每张图**只有一个观点**，说到位就停 |
| 钩子位置 | 前 5–10 帧 | **第 1 张**（它同时是封面） |
| 失败模式 | 节奏塌陷、中段拖 | 前 3 张没抓住 → 观众不再滑 |

## 2. 步骤

### 2.1 定信息骨架（先定张数，再定内容）

先写一句话的骨架声明，再拆张。三种可用骨架：

- **问题 → 拆解 → 结果**：第 1 张抛出用户的具体痛点（带数字），第 2–4 张拆痛点成因，最后 1–2 张给结果与数据。适合版本更新、性能发布。
- **清单 1..N**：N 个功能/技巧并列。第 1 张给"看完能拿到什么"，中间 N 张各说一条，最后 1 张收口（引导、CTA）。适合功能介绍。
- **单点深挖**：1 个功能讲透，3–5 张。第 1 张现象，第 2 张原理，第 3 张效果对比，第 4 张怎么用。适合单一爆点。

**张数**：推荐 **6–9 张**。少于 3 张时列表用首图 16:9 展示（见规格表），封面要按 16:9 安全区设计；3 张及以上时列表显示前 3 张缩略图裁成 2.35:1，**所以前 3 张各自都要能立住，且关键信息必须在中心区**。

### 2.2 出图

- **画布**：1080×1440（3:4）。从 `scripts/social_specs.json` 读尺寸，不要手写。
- **版式**：用 `assets/platforms/wechat/image-text/card.template.html`。它提供了标题区 / 正文区 / 页码与品牌区三段式结构 + 安全边距，改文案不要改骨架。
- **一次渲染多画幅**：如果同一批内容还要出视频号封面，把图卡与封面放进同一页并排、`viewport` 放大到容纳全部、再逐个 `el.screenshot()`——沿用视频线第 25–28 条的做法。
- **文字可读性**：图上的字号按**真实图片像素**算，正文 ≥ 32px（1080 宽画布上），标题 ≥ 72px。小字在手机上等于没有。
- **风格**：主色/字体/图形母题从 `DIRECTION.md` 读，与视频线一致。**但不要复用视频线的镜头手法**（发光地平线、粒子汇聚、字符场这类）——图卡是静态排版，硬套动态手法会变成无意义的装饰（对应视频线硬约束「不套模板」）。

### 2.3 逐图配文案

配套文案是**发布时写在图片之外**还是**画在图上**，取决于用户习惯，两种都交付更稳妥：

- **图上文字**：短、大、可单张独立成立。**建议 ≤60 字**（官方上限 2000 字，但没人会看完 2000 字的一格）。
- **配套文案（发布文案 / 说明）**：一句话段，允许比图上更完整。**图上与配套文案不要复述同一句话**——图上给结论，配套给依据与补充。

逐图文案模板：

```
[图 3] 图上：安装体积从 220MB 降到 48MB，冷启动快了 2 秒
       配套：我们用分层懒加载重写了打包器，首屏只拉起真正用到的模块。
```

**每个数字都要能回溯**（视频线硬约束「真实功能」）：在 `plan.json` 或单独的 `claims.md` 里记下数字来源。图文没有脚注位置，无法自证，所以**图文中出现的数字必须是长文里能查到出处的那些**。

### 2.4 首图/封面

系统会自动生成封面，但**不要依赖它**。首图自己按封面标准设计：

- 标题（≤ 一行，24 字内）+ 一个具体数字或结论。
- 关键信息全部落在**中心 2.35:1 安全区**内（前 3 张会被裁成 2.35:1 展示）。
- 不放 logo、不放纯装饰、不放二维码（二维码留到最后一张）。

### 2.5 自检

```sh
python3 <skill-dir>/scripts/check_social_delivery.py --project <content-dir> --forms wechat/image-text --strict
```

检查项：张数上限与推荐区间、每张宽高比是否 3:4、单图体积 ≤10MB、动图帧数 ≤300、标题字数 ≤64、图文字数、首图安全区（长宽比裁切后是否仍有内容）。

## 3. 常见问题

| 现象 | 原因 | 处理 |
|---|---|---|
| 发出去发现前 3 张被裁掉了标题 | 前 3 张按 3:4 满幅排版，未留 2.35:1 中心安全区 | 前 3 张的关键信息收进中心区；或改成 ≤2 张（走 16:9 首图规则） |
| 横滑到第 4 张完读率断崖 | 前 3 张没有递进，观众预判"后面也一样" | 每张必须有一个**新增**信息点，不能是同一观点的换图 |
| 图片在手机上糊 | 导出缩略图或 DPR 换算错误 | 交付前读图片头实测像素宽高（`check_social_delivery.py` 会报），不要信 CSS |
| 动图不动 | 总帧数超 300 | 砍帧或改静态图 |
| 文案被判定为标题党 | 图上数字无出处 | 数字必须来自长文/官网/真实测试；没有出处就改成定性表述 |
| 「到底能发几张」说不清 | 官方口径 9 张 / 20 张不一致 | 交付时写成"以后台编辑器实际提示为准"，推荐按 6–9 张设计，**不编造确定值** |

## 4. 交付清单

- `export/wechat/image-text/01..NN.jpg`（3:4，按横滑顺序命名）
- `export/wechat/image-text/copy.md`：标题候选 3 条（各 ≤64 字）+ 逐图文案（图上 / 配套两栏）
- `export/wechat/image-text/cover.jpg`：首图封面方案（若与 01 不同）
- `export/wechat/image-text/meta.json`：**自检脚本读它来校验字数**，必须交付，否则字数项只报警告：
  ```json
  {
    "form": "wechat/image-text",
    "title": "打包体积砍到 48MB",
    "cardTexts": ["第 1 张图上的文字", "第 2 张图上的文字"]
  }
  ```
- `export/wechat/image-text/check.json`：自检实测结果（`--json` 参数输出）
- 一句风险声明：哪些主张有出处、哪些是定性表述、哪些数字无法自证因此未使用

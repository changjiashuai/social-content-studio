# 生产管线 pipeline（跨平台共用底座）

所有平台包共用同一条管线：**取材 → 方向 → 出素材 → 渲染 / 编码 → 自检 → 交付**。
平台包只改"载体形态"（画幅、字数、封面比例、文案体裁），**不改这条管线**。

---

## 1. 四条共用纪律

| 纪律 | 含义 | 违反后果 |
|---|---|---|
| **取材同源** | 不做第二套产品调研。所有平台共用视频线第 3 步的仓库审计结果（真实功能、发布状态、证据）。**没有可追溯主张的内容不许发布。** | 不同平台出现互相打架的说法，可信度崩盘 |
| **方向先行** | 视频线的 `DIRECTION.md` 对全部平台生效：跨平台共用同一份主视觉规范（主色、字体、图形母题、口号），只在画幅与信息密度上分叉。多平台时这是强制项。 | 各平台看起来像不同品牌做的 |
| **规格机器校验** | 每个形式交付前跑 `scripts/check_social_delivery.py`，逐项对照 `scripts/social_specs.json`。**尺寸、比例、字数、文件大小一律不靠肉眼**——与视频线第 18/20/27 条（版面自检脚本化）同源。 | "我看着没问题"发布后被平台压扁/裁切/退回 |
| **字体不靠自定义字体** | 各平台都不保证加载外部字体，正文一律用系统字体栈（`-apple-system` / `BlinkMacSystemFont` / `PingFang SC` / `Microsoft YaHei`）。需要特殊字体时，把那一段做成图。 | 用户端字体回退，版面全乱 |

## 2. 管线七步（与视频线流程 1–7 步一一对应）

| 步 | 动作 | 平台无关的部分 | 平台相关的部分 |
|---|---|---|---|
| 1 | 确认范围、平台、形式 | 产品/仓库、受众、语言 | 由 `plan.json.selection` 决定；画幅由平台规格决定 |
| 2 | 初始化并检查环境 | 工程目录、依赖检查 | — |
| 3 | 调查产品、接通组件 | **完全相同**（视频线第 3 步原样执行） | — |
| 4 | 定方向、写 `DIRECTION.md` | **完全相同**（含专属手法推导、反重复） | 画幅规范按平台规格填写 |
| 5 | 逐镜头 / 逐图 / 逐段搭建 | 手法推导逻辑相同 | 载体形态不同（动态分镜 vs 静态图卡 vs 长文段落） |
| 6 | 配乐与音效 | **完全相同**（仅视频类形式需要） | 图文类形式跳过 |
| 7 | 审片 / 审稿并交付 | 出联系表、全尺寸帧、实读实看 | 平台的封面、文案、话题按平台文档补齐 |

**关键**：第 3、4 步在整条链路里**只做一次**，无论选了多少平台。这是"多做一次调研"与"多平台各自为战"的分界线。

## 3. 渲染与编码底座

所有平台的图卡、封面、视频都走同一条底座，不另起一套：

| 环节 | 做法 | 出处 |
|---|---|---|
| 静态出图 | 无头 Chrome + puppeteer-core，`deviceScaleFactor: 1`，元素级 `el.screenshot()` | `scripts/render_social_assets.mjs` |
| 一次多画幅 | 多张卡片放同一 HTML 页面并排 → 视口放大到容纳全部 → 逐个元素截图 | 视频线第 25–28 条 |
| 视频编码 | `ffmpeg -framerate N -i frames/f%05d.jpg -i mix.wav -c:v libx264 -crf 18 -pix_fmt yuv420p -movflags +faststart -c:a aac -b:a 192k -shortest` | 视频线本机实测管线 |
| 音频响度 | 峰值归一化后再过 `ffmpeg loudnorm`（两遍），目标 `I=-15 / TP=-1.5`，显式 `-ar 44100` | 视频线第 21 条 |
| 画面自检 | 硬字幕条、安全边距都靠扫帧实测，不靠 CSS 估算 | 视频线第 18/20/27 条 |

## 4. 跨平台媒体标准

| 项 | 标准 | 说明 |
|---|---|---|
| 视频编码 | **H.264**（`libx264`）+ `yuv420p` + `-movflags +faststart` | H.265 在 Windows Chrome/Edge 不能播放；全平台稳妥选 H.264 |
| 视频帧率 | 25 或 30 | 与源帧率一致，不插帧 |
| 分辨率下限 | 短边 **≥1080px**（1080p 口径） | `1920×1080` 与 `1080×1920` 都算；`720×1280` 不算 |
| 音频 | AAC 192kbps，44.1kHz | — |
| 图片色彩 | sRGB，不投 HDR | — |
| 图片体积 | 每张 **≤10MB**（小红书单图上限 20MB，仍按 10MB 控制更稳） | 各平台具体上限见平台文档 |
| 图片格式 | 静态 jpg/png；动图 gif（**小红书与视频号图片形式都不支持 GIF**，微信图文支持但总帧数 ≤300） | — |
| 字体 | 系统字体栈，见 §1 | — |

平台专属的数值不写在这里，写在 `scripts/social_specs.json` 对应平台的节点里。

## 5. 验收纪律（自动检查证明什么、不证明什么）

沿用视频线硬约束「授权与真实验收」：

- **自动检查只证明**：尺寸、比例、体积、字数、编码、禁用项等**结构性事实**。
- **自动检查不证明**：视觉效果、语义正确性、平台真实渲染效果（尤其公众号粘贴后的样式、手机预览、小红书的封面裁切预览）。
- **交付时必须说清**：哪些是脚本验过的、哪些是人工看过的、哪些**仍未验证**。
- 没有实际审阅就说"已验收"，是本工作区最严重的交付问题。

### 5.1 内容溯源是内部核查（全部形式适用）

形式规格由脚本管，**事实出处由 `evidence/FACTS.md` 管**，两者不重叠。

- 上屏的每个数字、每条事实性主张，在内容目录的 `evidence/FACTS.md` 有一行：主张 / 上屏内容 / 来源 / 引用或测量方法 / 状态。
- **多形式只写一份**：它放在内容目录，不在各 `export/<平台>/<形式>/` 下——正好支撑「事实源 → 静态 → 动态」的口径一致链。改数字先改 FACTS，再改各处产出。
- 状态只有三种：`已核实` / `示意` / `待核实`。标「示意」的**不许**配「实测」「官方数据显示」一类措辞。
- **这是内控文件，不进交付清单、不主动展示**。用户问起来源如实回答；证据链断裂时用一句话说明结论，不必透出整张表。
- 契约与示例见 [内部溯源](../platforms/generic/motion-film/provenance.md)；脚本的分级判断见 [generic/specs.md](../platforms/generic/specs.md) §3。

## 6. 本机实测管线（复用视频线 1–28 条）

`SKILL.md` 视频线章节的 28 条本机实测经验对**全部平台包**适用（沙箱、headless 旧模式、zsh 通配符、loudnorm、mask-image 等）。
平台相关的追加条目见各平台文档的「本机实测」小节，聚焦它们各自的易错点：

- **微信**：图卡与封面的像素尺寸必须实测（`deviceScaleFactor` 不为 1 时截图会翻倍）；正文 HTML 片段要过白名单体检；长文必须扫手机预览二维码。
- **小红书**：封面会被信息流裁切，安全区要实测；话题标签数与字数要脚本化核对；**站外导流措辞**必须逐条排查。

---

## 7. 与平台包的关系（一句话）

> **`core/` 定义"怎么做"，`platforms/<平台>/` 定义"做成什么样"。**
> 新增平台时只写 `platforms/<平台>/` 与它自己的规格节点/模板/检查函数，`core/` 保持不变。
